# Modelos Melhores, Ferramentas Piores: O Paradoxo Contraintuitivo que Está Quebrando os Assistentes de IA para Programação

> "O cinto de tolerância absorve completamente o erro e há pouco gradiente contra inventar um apelido, adicionar um campo perdido ou usar um nome de parâmetro próximo."
>
> — Armin Ronacher

Aqui vai uma frase que você não espera ler em 2026: os modelos Claude mais novos são piores em chamar ferramentas do que os antigos.

Não piores em raciocinar. Não piores em escrever texto ou depurar lógica complexa. Piores na tarefa aparentemente simples de emitir um payload JSON válido que corresponda a um schema que lhes foi dado. Piores na coisa que todo assistente de IA para programação faz dezenas de vezes por sessão.

Armin Ronacher — criador do Flask, Jinja2, e do novo agente de codificação Pi — passou dois dias perseguindo um bug que não deveria existir. Modelos Anthropic mais novos, incluindo o Opus 4.8 e o Sonnet 5, estavam repetidamente inventando campos falsos ao chamar a ferramenta de edição de arquivos do Pi. Campos como `requireUnique`, `oldText2`, `type`, `kind`, `forceMatchCount`, e até `event.0.additionalProperties`. O conteúdo da edição em si estava perfeito byte a byte. O modelo entendeu a tarefa. Só não conseguiu resistir em decorar o JSON com metadados fictícios.

Os modelos mais antigos? Lidavam com o mesmo schema sem problema algum.

Isso não é um glitch aleatório. A investigação de Ronacher aponta para algo mais profundo e desconfortável: os modelos não estão deteriorando. Eles estão se adaptando. Estão se adaptando a um mundo onde chamadas de ferramentas levemente malformadas ainda têm sucesso porque o cinto de tolerância silenciosamente as repara. E essa adaptação está deixando eles piores em interagir bem com as ferramentas de qualquer outra pessoa.

Bem-vindo ao paradoxo de modelos melhores e ferramentas piores.

## A Descoberta: Quando o Opus 4.8 Começa a Alucinar Argumentos de Ferramentas

O bug apareceu no Pi, o agente de codificação em desenvolvimento de Ronacher. O Pi usa uma ferramenta de edição aninhada que aceita um array `edits[]`, onde cada entrada é um objeto com exatamente dois campos: `oldText` e `newText`. Direto e reto.

Só que o Opus 4.8 e o Sonnet 5 estavam produzindo entradas assim:

```json
{
  "oldText": "texto para substituir",
  "newText": "texto de substituição",
  "requireUnique": true
}
```

Ou assim:

```json
{
  "oldText": "...",
  "newText": "...",
  "oldText2": "",
  "newText2": ""
}
```

Ao longo de várias tentativas, Ronacher catalogou um "zoológico inteiro de chaves inventadas no final": `type`, `id`, `kind`, `unique`, `matchCase`, `in_file`, `children`, `notes`, `cost`, e até `event.0.additionalProperties`.

A parte mais irritante? Os payloads reais de `oldText` e `newText` estavam corretos. O modelo tinha resolvido o problema. Só não conseguiu parar de enfeitar o JSON com metadados inventados.

Ainda mais estranho, a falha era dependente de contexto. Um prompt limpo de uma só rodada como "edite esse arquivo" funcionava de boa. Só aparecia em conversas longas e agênticas onde o modelo já tinha lido arquivos, diagnosticado um problema e composto uma edição de várias linhas. E mesmo assim, não sempre — cerca de 20% das vezes nos registros que reproduziram o problema.

Retirar os "blocos de raciocínio" do histórico da conversa reduzia pela metade a taxa de falha. Ativar o modo de chamada de ferramentas rigorosa da Anthropic eliminava o problema por completo.

Essa última pista é importante. O modelo *pode* seguir o schema quando forçado. Só que não quer.

## Por Que Está Ficando Pior: A Teoria do Artefato de Treinamento

A hipótese mais forte de Ronacher não é um bug nos pesos do modelo. É um artefato de treinamento.

Aqui vai a cadeia de lógica: modelos Anthropic mais antigos foram treinados com exemplos de chamada de ferramentas, mas esses exemplos vieram de uma época anterior à existência do Claude Code como cinto de tolerância dominante. Os modelos aprenderam padrões gerais. Conseguiam se adaptar a diferentes formas de ferramentas porque seu treinamento era relativamente diverso.

Modelos Anthropic modernos são quase certamente pós-treinados dentro de um ambiente parecido com o Claude Code. O modelo aprende como uma chamada de ferramenta bem-sucedida se parece *naquele cinto específico*. Também aprende quais erros são tolerados — porque o Claude Code tolera muita coisa.

Ao inspecionar o código minificado do cliente do Claude Code, Ronacher descobriu que ele é extraordinariamente tolerante. Verifica se há marcações `<invoke>` vazadas no texto visível do modelo e tenta novamente chamadas ruins com sua própria máquina de estados. Repara escapes Unicode quebrados e surrogates solitários. Aceita apelidos de parâmetros: `old_str` funciona junto com `old_string`, `path` funciona no lugar de `file_path`. Filtra silenciosamente chaves inesperadas. Nem mesmo usa o modo rigoroso da Anthropic, porque a Anthropic aplica limites de complexidade em definições de ferramentas que fazem requisições de API falharem.

Em outras palavras, o Claude Code é um **cinto de tolerância**. Ele treina o modelo de que a imprecisão é de graça.

Se o aprendizado por reforço acontece em um ambiente onde chamadas levemente malformadas ainda completam a tarefa e recebem recompensa, não há gradiente empurrando o modelo em direção à precisão. Por que ele aprenderia a respeitar um schema quando o cinto absorve todo desvio? O modelo descobre que adicionar um apelido, inventar um campo plausível ou usar um nome de parâmetro próximo não bloqueia o sucesso. Então o comportamento é reforçado.

"O cinto de tolerância absorve completamente o erro," escreve Ronacher, "e há pouco gradiente contra inventar um apelido, adicionar um campo perdido ou usar um nome de parâmetro próximo."

## O Problema da Distribuição Fora do Padrão

Isso seria apenas irritante se afetasse só usuários do Claude Code. Mas não afeta. Afeta todo mundo que constrói ferramentas que *não* são o Claude Code.

A ferramenta de edição do Claude Code é comparativamente simples: `file_path`, `old_string`, `new_string`, e uma flag opcional `replace_all`. A ferramenta de edição do Pi é aninhada: um array `edits[]` de objetos com `oldText` e `newText`. Mesma intenção semântica, forma diferente.

Para um modelo pós-treinado no schema simples do Claude Code, o schema aninhado do Pi é cada vez mais **fora da distribuição**. O modelo tem um prior muito forte sobre como uma chamada de ferramenta de edição deveria se parecer, e esse prior é a forma do Claude Code. Quando confrontado com um schema diferente, não se adapta de forma limpa. Ele resiste.

"Quando o Opus 4.5 lançou, ele se adaptava excepcionalmente bem a outras ferramentas de edição," observa Ronacher. "Agora estou um pouco preocupado com o caminho que estamos tomando. Schemas de ferramentas alternativos podem não ser apenas desconhecidos. Podem ser implicitamente punidos pelo pós-treinamento que otimiza para uma ecologia de ferramentas particular e tolerante."

Essa ecologia não é documentada. A Anthropic publica um formato de ferramenta de editor de texto, mas o Claude Code na verdade não segue ele. O que o Claude Code faz internamente é oculto, de código fechado e invisível para todo desenvolvedor que constrói em cima da API.

A implicação é perturbadora: **schemas de ferramentas não são mais contratos neutros.** Eles estão em algum lugar na distribuição do modelo, e algumas formas estão perto do que o modelo viu durante o pós-treinamento enquanto outras estão distantes. O modelo pode ser inteligente o suficiente para entender seu schema e ainda assim ser ruim em amostrar a forma exata sob pressão — porque seu treinamento ensinou que a precisão não importa.

## O Padrão Mais Amplo: Entendimento É o Novo Gargalo

A descoberta de Ronacher não é uma peculiaridade isolada. É parte de um padrão mais amplo que várias pessoas estão notando simultaneamente.

Geoffrey Litt, engenheiro de design na Notion, deu uma palestra amplamente compartilhada intitulada **"Entendimento é o novo gargalo."** Seu argumento: à medida que agentes de IA escrevem cada vez mais código, o fator limitante não é mais a velocidade de escrita, mas a compreensão humana.

"Um projeto é muitas, muitas rodadas com o agente," observa Litt. "E o entendimento que você tem do sistema é parte da sua capacidade de surgir com a próxima ideia para evoluí-lo."

Litt conecta isso ao conceito de **dívida cognitiva**, popularizado pela pesquisadora de engenharia de software Margaret-Anne Storey e pelo desenvolvedor Simon Willison. Dívida cognitiva é o que se acumula quando desenvolvedores perdem a noção de como seus sistemas funcionam. O código compila, os testes passam, mas ninguém consegue explicar por que certas decisões de design foram tomadas ou como diferentes partes interagem. Com código gerado por IA, essa dívida se acumula na velocidade da máquina.

Mark Zuckerberg reforçou a mesma ansiedade do alto escalão corporativo. Durante uma reunião interna do Meta no início de julho de 2026, ele disse aos funcionários que os agentes de IA "não progrediram tão rápido quanto ele esperava." Os cortes de empregos no início do ano, parte da reestruturação focada em IA da Meta, não produziram o retorno esperado. Zuckerberg projetou melhorias em três a seis meses — um prazo notavelmente cauteloso para alguém que normalmente age rápido e quebra coisas.

O padrão é consistente em toda a pilha: os modelos estão ficando melhores na *tarefa* e piores na *interface*. Estão ficando melhores em raciocinar problemas complexos e piores em comunicar seu raciocínio através de chamadas de ferramentas precisas e interoperáveis. Estão ficando melhores em escrever código e piores em ajudar humanos a entender o que escreveram.

## A Decodificação Restrita Pode Corrigir Isso?

Uma solução óbvia é a **decodificação com gramática** — também chamada de decodificação restrita. Em vez de pedir ao modelo para produzir JSON válido e torcer para dar certo, você restringe o amostrador para que tokens inválidos sejam fisicamente impossíveis de emitir.

Se o schema diz que só `oldText` e `newText` são permitidos dentro do objeto de edição, o amostrador mascara todos os outros tokens nessa posição. O modelo literalmente não consegue inventar `requireUnique` porque o token não está no conjunto permitido.

Os novos modelos `gpt-oss` da OpenAI dão um passo nessa direção com seu formato de resposta **Harmony**. O modelo pode expressar em banda que o corpo da mensagem é JSON (`<|constrain|>json`), e a pilha de inferência pode mudar para amostragem JSON restrita para aquela região. Para modelos GPT hospedados, desenvolvedores podem até fornecer gramáticas LARK personalizadas para ferramentas que precisam de formas mais rigorosas.

O modo `strict` da Anthropic parece fazer algo similar do lado do servidor — Ronacher nota que ativá-lo eliminou completamente o problema de chaves inventadas — mas a Anthropic também aplica limites de complexidade em definições de ferramentas no modo rigoroso, e é por isso que o Claude Code não o usa.

Os priors de Ronacher mudaram. Ele costumava ser cético da invocação rigorosa com gramática restrita porque decodificação restrita pode ter tradeoffs de qualidade. Depois desse bug, ele está significativamente mais convencido. "Se os modelos mais novos ficam melhores em resolver a tarefa enquanto ficam piores em emitir fielmente um schema de ferramenta alternativo, então o cinto de tolerância precisa de garantias mais fortes em algum lugar."

A questão é: de quem é a responsabilidade de impor essas garantias? O provedor do modelo? O construtor do cinto de tolerância? O desenvolvedor que projetou o schema da ferramenta?

No momento, a resposta é confusa. Os modelos da Anthropic são fechados. Seu cinto de tolerância é fechado. A documentação da ferramenta de editor de texto não corresponde ao que o Claude Code realmente faz. E desenvolvedores que constroem em cima da API ficam adivinhando quais formas de ferramentas vão funcionar e quais vão desencadear priors invisíveis de um processo de treinamento que não podem ver.

## O Que Isso Significa para o Futuro

Se essa tendência continuar, as implicações são profundas.

Primeiro, **a interoperabilidade de ferramentas pode na verdade diminuir à medida que os modelos melhoram.** Gostamos de imaginar que modelos melhores são mais gerais, mais adaptáveis, mais capazes de seguir instruções arbitrárias. Mas se o pós-treinamento está cada vez mais concentrado dentro de um cinto de tolerância dominante — Claude Code, ou o equivalente na OpenAI — então os modelos ficarão *mais* especializados, não menos. Eles serão de classe mundial nas formas de ferramentas canônicas e cada vez mais erráticos em tudo o mais.

Segundo, **cintos de tolerância de código fechado viram padrões de facto.** Mesmo que o Claude Code não seja open source, suas peculiaridades estão sendo incorporadas nos modelos que todo mundo usa. Ferramentas alternativas terão que herdar essas peculiaridades ou lutar uma batalha difícil contra priors invisíveis. Essa é uma forma sutil de lock-in de ecossistema que não tem nada a ver com APIs ou preços.

Terceiro, **o problema da imprecisão se estende além da chamada de ferramentas.** Se os modelos aprendem que erros são silenciosamente reparados, podem ficar mais descuidados em outros domínios também: citações, aritmética, afirmações factuais. O cinto de tolerância vira uma muleta, e o modelo nunca aprende a andar reto.

Quarto, **o entendimento humano vira a vantagem competitiva definitiva.** Como argumenta Litt, os desenvolvedores que vão prosperar são aqueles que conseguem construir modelos mentais eficientes de sistemas gerados por IA. Documentos explicadores de código. Micro-mundos interativos. Quizzes de entendimento. Isso não são luxos. São habilidades de sobrevivência.

## Conclusão: O Preço da Conveniência

Há uma máxima antiga da engenharia: facilite o que é fácil e torne possível o que é difícil. O cinto de tolerância inverte isso. Ele torna o que é fácil trivialmente fácil absorvendo todo erro — e, ao fazer isso, torna o que é difícil impossível treinando o modelo de que erros não existem.

O relatório de bug de Armin Ronacher é mais do que uma curiosidade técnica. É um sinal de alerta. As ferramentas de IA que estamos construindo não são apenas interfaces entre humanos e modelos. Elas são ambientes de treinamento. Cada peculiaridade, cada reparação silenciosa, cada erro perdoado é uma lição que o modelo internaliza. E essas lições não ficam dentro do cinto de tolerância. Elas vazam para cada chamada de ferramenta, cada interação de API, cada integração com um sistema de terceiros.

Modelos melhores deveriam significar ferramentas melhores. Mas se esses modelos são treinados dentro de ecossistemas tolerantes que escondem seus erros, o resultado é o oposto: modelos que são brilhantes em raciocinar e descuidados em comunicar. Modelos que resolvem o problema e depois sabotam a solução com uma flag `requireUnique` fictícia.

A correção não é tornar os modelos menos capazes. É tornar os cintos de tolerância mais honestos. Schemas rigorosos. Erros visíveis. Decodificação restrita por gramática. Chamadas de ferramentas que falham alto em vez de silenciosamente, para que o modelo aprenda que a precisão importa.

Porque a alternativa — um mundo onde cada ferramenta de IA herda os vieses invisíveis de um único cinto de tolerância de código fechado — não é um futuro que ninguém queira depurar.
