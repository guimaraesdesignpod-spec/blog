# What xAI's Grok Build CLI Actually Sends to Your Codebase: A Wire-Level Privacy Teardown

On July 12, 2026, a security researcher published what may be the most thorough reverse-engineering of an AI coding tool yet. Using a man-in-the-middle proxy, they captured every byte that xAI's Grok Build CLI sends back to its servers. The headline is not that Grok sends code — every cloud coding agent does that. The headline is *what* it sends, *how much* of it, and the fact that you cannot turn it off.

If you have Grok Build installed and you've ever run it in a directory containing anything sensitive, this article is for you. The findings are reproducible, documented with SHA-256 hashes, and paint a picture of data collection that goes far beyond what the CLI's setup materials suggest.

## The Setup: How Someone Reverse-Engineered a Closed Binary

The researcher, operating under the handle cereblab, started with a simple question: when I run `grok -p "fix this bug"` in my project directory, what exactly leaves my machine?

To answer it, they built a controlled environment:

- **macOS on Apple Silicon**, running Grok Build CLI version **0.2.93** (SHA-256: `2a97ba675bd992aa9b981e2e83776460d94f469b510c0b8efe28b50d236d767c`)
- **mitmproxy** to intercept all HTTPS traffic, with xAI's certificate trusted in the login keychain
- A **throwaway repository** containing fake "canary" secrets with unique markers (like `CANARY7F3A9-SECRET`) so anything appearing in captured traffic could be traced unambiguously back to a specific file
- The canary values were not real credentials — they were purpose-built strings designed to prove whether specific files were being exfiltrated

This is not theoretical. Every finding below is backed by a captured wire artifact with a SHA-256 hash. The researcher even published the reproduction commands so anyone with the same binary version can verify it themselves.

## Finding 1: Your Secrets Are Sent Verbatim and Unredacted

When Grok reads a file — any file it considers relevant to your task — that file's contents are transmitted to xAI in two separate channels simultaneously.

**Channel A** is the model-turn channel: a `POST /v1/responses` request that carries the conversation context to the LLM. Inside this 48KB request body, the researcher found their fake `.env` secrets **verbatim**:

```
API_KEY=CANARY....5
DB_PASSWORD=CANARY....PASS
```

All six planted file markers were recoverable from the decrypted request bodies. No redaction. No encryption of sensitive fields. A `.env` file is treated the same as a `README.md`.

**Channel B** is a persisted archive: the same content is packaged into a `session_state` tarball and uploaded via `POST /v1/storage`, returning HTTP 200. When the researcher decompressed the staged artifact before it drained, every canary marker was present — including the ones from the secrets file.

The researcher was careful to preempt a common objection: "But you told it to read the secrets." They ran a control test with a file the agent was explicitly told **not** to open (`untouched_secret.txt`) and the prompt "Reply exactly OK, do not read any files." The untouched file's marker appeared in **neither** channel. The leak is scoped to files Grok *does* read — but it reads liberally, and it applies **zero redaction** to what it finds.

Importantly, the researcher noted one gap in their testing: the `.env` file was git-tracked. They did not separately test whether a `.gitignore`d file is still uploaded. The mechanism appears read-driven, but that specific case remains untested.

## Finding 2: Your Entire Repository Is Uploaded — Even Files You Never Asked It to Read

This is where things escalate from "concerning" to "unprecedented."

The researcher discovered that Grok Build uploads a **complete snapshot of your repository** via a separate mechanism from the model-turn channel. And this snapshot includes **every tracked file**, not just the ones the agent reads.

The evidence is in three layers:

**Layer A — The byte split.** In a test with a 12 GB repository of random files the agent never read, the two channels moved wildly different volumes:

- **Channel A** (`/v1/responses`, model turns): **192 KB total** across 5 requests
- **Channel B** (`/v1/storage`, repo snapshot): **5.10 GiB** across 73 chunks of ~75 MB each

That's a **27,800× ratio**. The model demonstrably never ingested those files — 192 KB cannot carry 5 GiB — yet 5.1 GiB of them left via `/v1/storage`. Every single one of the 82 storage requests returned HTTP 200. Zero failures.

**Layer B — The binary's own confession.** Running `strings` on the Grok binary revealed source paths from a Rust crate called `xai-data-collector`, with constants like:

```
crates/codegen/xai-data-collector/src/gcs.rs
crates/codegen/xai-data-collector/src/storage_client.rs
crates/codegen/xai-grok-shell/src/upload/{grok,turn,trace,manifest}.rs
grok-code-session-traces
storage.googleapis.com
"Uploading bytes to GCS via proxy"
```

This is first-party code, not a third-party analytics library. xAI built this data collection pipeline intentionally.

**Layer C — The smoking gun.** On a real 298-file codebase, the researcher used a SuperGrok account (quota lifted) with the prompt: "Reply with exactly: OK. Do not read or open any files." They had planted a unique marker in `src/_probe/never_read_canary.txt`.

Grok uploaded the **entire repository as a git bundle** via `POST /v1/storage → 200`. Running `git clone` on the captured bundle reconstructed the repo. And `src/_probe/never_read_canary.txt` contained the marker **verbatim** — a file the agent was explicitly told not to open. The bundle also carried the full git history (4 commits, 47 files).

They replicated this on a second, unrelated codebase with the identical result.

The upload mechanism is a **git bundle**. "Whole repo" is literal: every tracked file plus the entire commit history. The only ceiling found was a model-usage quota (402/429 on `/v1/responses`), not a storage size cap.

## Finding 3: The Destination Is a Named Google Cloud Storage Bucket

The data does not vanish into an abstract "cloud." It goes to a specific, named bucket: **`grok-code-session-traces`** on Google Cloud Storage.

This is proven by:
- Binary strings naming the bucket explicitly
- Staged `metadata.json` files showing per-file destinations of the form `gs://grok-code-session-traces/repo_changes_dedup/v2/…/sha256_…`
- Direct `PUT` requests to `storage.googleapis.com` observed during testing
- The multi-GB upload artifacts returning 200

It is not AWS S3. It is not a transient cache. It is a persistent GCS bucket, and your code is content-addressed and stored there.

The researcher also found third-party telemetry being sent to Mixpanel (`api.mixpanel.com/track`) and xAI's own events endpoint (`grok.com/_data/v1/events`), both returning 200.

## Finding 4: "Improve the Model" Being Off Makes No Difference

This may be the most disturbing finding. xAI offers a privacy toggle in settings: "Improve the model." The natural assumption is that turning this off stops your data from being collected.

It does not.

The researcher ran Grok with "Improve the model" explicitly **disabled**. The result:

- The entire repo was still uploaded as a git bundle (`POST /v1/storage → 200`)
- The server's `/v1/settings` response to the CLI still returned:
  ```json
  "trace_upload_enabled": true,
  "upload_enabled": true,
  "session_registry_enabled": true
  ```
- The opt-out governs **training**, not **storage**. Your code still leaves your machine and is still accepted into the GCS bucket.

This is a critical distinction that xAI's privacy policy and CLI setup materials do not make clear. The researcher reviewed the install script and quickstart and found no mention of the `repo_state` upload mechanism, the `~/.grok/upload_queue` staging directory, or the `grok-code-session-traces` bucket. The mechanism is active by default on standard consumer logins.

## How the Researcher Stayed Honest About What They Didn't Prove

One of the most impressive aspects of this disclosure is the "What we did NOT prove" section. The researcher was explicit about the limits of their findings:

- **They did not prove xAI trains on this data.** Upload and storage are measured facts. Whether that data is used for model training is a policy question outside the scope of the wire capture.
- **Some artifacts were observed live but not retained.** The 64 MB, 600 MB, and 3 GB test runs were observed during a sweep but their capture logs were overwritten. Only the 12 GB run was retained as a file.
- **The 12 GB capture was stopped mid-stream.** It proves multi-GB upload succeeds with no failures, not that a 12 GB repo completes end-to-end.
- **The "not documented" claim is scope-limited.** The researcher based it on the CLI's install script and quickstart, not an exhaustive audit of all xAI documentation.
- **The mechanism was not tested with .gitignore** to see whether ignored files are still swept up.

This intellectual honesty makes the findings more credible, not less. Where there is a gap, they say so. Where there is proof, they provide SHA-256s and reproduction steps.

## The Industry Context: How Other Tools Handle Privacy

The Hacker News discussion that followed this disclosure included a notable contribution from a **GitHub Copilot engineer** who works on identity, safety, and privacy.

They confirmed that:
- Microsoft employees need a separate onboarding process to access *any* GitHub company resources
- Very few employees within GitHub proper have access to view private repositories
- In rare cases where access is needed for legal or safety reasons, the repository owner is notified
- There are currently **no OpenAI employees with access to GitHub systems**
- About **4 layers of protection** exist between OpenAI and private GitHub repos

Contrast this with Grok Build: one binary, one login, zero approval gates, and your entire codebase goes to a single named bucket. The Copilot engineer's point was not to say GitHub is perfect — they acknowledged that nothing can be proven with absolute certainty — but to show that **architectural privacy guardrails are possible**, and Grok Build appears to have none of them.

## What Developers Should Do Now

If you use or have considered using Grok Build, here are the practical takeaways:

**1. Never put real secrets in .env files within an AI agent's reach.** This has always been good practice, but Grok's lack of redaction makes it non-negotiable. Use a secrets manager, environment variables injected at runtime, or a separate repo for sensitive configuration.

**2. Sandbox your AI agents.** Tools like bubblewrap, firejail, and gvisor can restrict what directories an AI CLI can read. One HN commenter described running Grok inside a bubblewrap container with a read-only system root and a tmpfs home, plus a filtering HTTP proxy on a Unix socket that only allows LLM provider domains. This is not paranoia — it is defense in depth.

**3. Prefer API-based tools over native proprietary CLIs.** When you use an API client like OpenRouter or a local tool with your own API key, you control exactly what data leaves your machine. The trade-off is performance — native CLIs often have tighter integrations — but the privacy gap is real.

**4. Audit what you already have installed.** If you installed Grok Build and ran it in any directory containing sensitive code, that code has already been uploaded. There is no recall button. xAI's privacy policy states that opt-outs are prospective, not retroactive.

**5. Demand transparency.** The core issue here is not that xAI collects data — every cloud service does. The issue is that the mechanism, scope, and persistence of collection are not disclosed in the CLI's own materials. Users cannot make informed consent decisions about what they do not know exists.

## The Bottom Line

The Grok Build CLI privacy disclosure is a case study in how AI tooling can outpace user understanding. What looks like a helpful coding assistant is, under the hood, a data collection pipeline that uploads your entire repository — secrets, history, and all — to a persistent cloud bucket. The toggle you thought protected you does not. The documentation you read does not mention it. And the only reason we know any of this is because one researcher spent days intercepting bytes and publishing their work.

This is not a bug. This is architecture. And it is architecture that every developer using AI coding tools needs to understand before they type their next prompt.
