# Why Your Local LLM Feels Dumber Than It Is

## The Gap Between Benchmark Hype and Living-Room Reality

You have seen the headlines. Qwen 3.8 27B scores within reach of frontier models on MMLU and HumanEval. A MacBook Pro can run it at fourteen tokens per second. The local AI revolution is here, and the cloud is optional. So you download the GGUF, fire up Ollama or vLLM, paste in a prompt, and wait.

The result feels... off.

Not dramatically wrong, but subtly worse than the same model on ChatGPT or Claude. Tool calls that worked in the API demo now fail silently. Reasoning traces loop back on themselves. After forty thousand tokens, the model seems to forget what it was doing. You check the benchmarks again. Same weights. Same model card. What is going on?

A research thread posted to the Level1Techs forum — and subsequently upvoted to 417 points on Hacker News with 171 comments — offers the most detailed public answer yet. The author, a hardware and inference engineer who goes by the handle `wendell-adjacent`, ran a systematic, logit-level investigation into why the same weights produce such different results depending on how you run them. The short version: the model is fine. The math surrounding it is not.

## The Oversimplification We All fell For

When people compare local and cloud LLMs, they usually compare weights and parameters. A 27-billion-parameter model is a 27-billion-parameter model, right? If you quantize it to four bits, you lose some precision, but the Internet wisdom says modern quantization is "almost lossless" for practical purposes. The model cards on Hugging Face advertise impossibly low KL divergence numbers. Case closed.

The Level1Techs research explodes this assumption. The author starts with a simple observation: "Every single instance of hardware and software running an LLM today is a little bit different. Or a lot different." Your GPU has a different instruction set than mine. The CUDA kernel that multiplies matrices on an RTX 4090 is not the same one running on an RTX PRO 6000 Blackwell. The attention backend that vLLM selects for your workload depends on your tensor shape, your sequence length, and whether you have prefix caching enabled. The nightly vLLM container the author pulled had 734 packages in it. That is 734 codebases, each with bugs and undocumented quirks, through which your prompt must travel before it becomes a token.

The research uses Qwen3.6-27B as its test subject — a dense, non-MoE model with 64 layers arranged in a repeating pattern of three Gated DeltaNet layers followed by one full-attention layer. The author captures full-vocabulary logits in BF16 every 32 prompt tokens across a roughly 100,000-token real-world agentic workload containing multiple tool calls. This is not a synthetic needle-in-a-haystack test. It is actual work product, chosen specifically because it does not appear in any public benchmark or training dataset. Nobody could have calibrated their quant for it.

## Test 1: Attention Backends Disagree — A Lot

The first experiment isolates one variable. Everything stays identical — BF16 weights, BF16 KV cache, same GPU, same software version — except the attention backend used for the 16 full-attention layers. The three backends tested are FlashAttention 2, Flash Inference, and Triton Attention.

For the first several thousand tokens, all three backends agree on the next token. Then, as context accumulates, they begin to diverge. By the 88,000-token mark, FlashAttention 2 and Flash Inference are flipping the top-1 token — the model's highest-confidence next word — in a significant fraction of sampled positions compared to the Triton baseline. The disagreements appear in clusters and vary with prompt content, rather than increasing smoothly with length. This is not a universal "model falls apart at 40k tokens" threshold. It is stochastic, content-dependent, and entirely invisible unless you are measuring logits.

Crucially, the author ran same-backend repeatability controls. Running the exact same test twice with the same backend produced bit-for-bit identical logits. The divergence is therefore not random noise. It comes exclusively from the matrix multiplication and addition operations happening inside the different attention implementations. The math is different, so the answer is different.

For a user, this means that switching from one inference engine to another — say, from vLLM to llama.cpp, or from FlashAttention to Triton — can change which token the model outputs. Not just the sampling randomness. The actual greedy argmax. In agentic workflows where a single flipped token can derail a tool call or trigger a reasoning loop, this is not academic. It is the difference between a working agent and a broken one.

## Test 2: KV-Cache Quantization Is a Silent Killer

The second experiment isolates the KV cache. The weights and activations stay at BF16. Only the KV cache is compressed — the memory buffer that stores keys and values from previous tokens so the model does not have to recompute them.

The results are stark. With a BF16 KV cache, the model completes tool calls correctly. With an INT8 KV cache, it eventually recovers from errors but not before botching the syntax. With an INT4 KV cache, it fails entirely — the tool call is never closed, and the model outputs gibberish. The author shows a screenshot of a real reproducible failure: BF16 succeeds, INT8 stumbles but recovers, INT4 dies.

This is the "your LLM's IQ drops like a rock after 40k tokens" phenomenon that local users have anecdotally reported for years. It is not the model running out of context. It is the KV cache losing precision, causing top-token flips that compound across layers until the output becomes incoherent. The effect is worse for agentic tasks with tool calls because a single malformed JSON bracket or missing closing tag is enough to crash the entire workflow.

## Test 3: Weight Quantization Is Not Created Equal

The third and most revealing experiment compares five different weight formats for the same Qwen3.6-27B checkpoint:

1. BF16 reference (unquantized)
2. Official FP8 (E4M3, W8A8)
3. Community INT8 (W8A16, static symmetric)
4. NVIDIA NVFP4 (mixed FP8 + NVFP4)
5. AWQ INT4 (W4A16, asymmetric)

Each of these uses a different CUDA kernel for matrix multiplication. BF16 uses standard PyTorch linear. FP8 uses CutlassFp8BlockScaledMMKernel. INT8 uses MarlinLinearKernel. NVFP4 uses a mix of FlashInferFP8ScaledMM and MarlinNvFp4. The kernels are different, the precision is different, and the results diverge accordingly.

The community INT8 (W8A16) — created by a user called TheHouseOfTheDude with no calibration dataset — outperforms the official FP8 checkpoint from Qwen's own Hugging Face repository. It also outperforms NVIDIA's official NVFP4 release, which comes in dead last. By 88,000 tokens, NVFP4 has flipped roughly 50% of top-1 tokens relative to the BF16 baseline.

In practical terms, both NVFP4 and AWQ INT4 failed to close their tool calls correctly in the author's test workload. The model was supposed to execute `show arp` and instead ran `show run`. FP8 and INT8 completed the correct calls. The gap between "works" and "breaks" is not gradual. It is a cliff, and some quants fall off it.

The takeaway is uncomfortable: the quantization method advertised on the model card may not be the one that actually preserves the model's capabilities. Impossibly low KL divergence claims are meaningless without full disclosure of the reference checkpoints, runtime environment, evaluation text, calibration data, and aggregation methodology. Most model cards provide none of these.

## What This Means for Local AI Users

If you are running local LLMs, the research suggests three practical lessons.

**First, your inference engine matters as much as your weights.** Ollama, vLLM, llama.cpp, and SGLang are not interchangeable precision-wise. They use different attention backends, different kernel fusion strategies, and different default quantization behaviors. If a model "feels dumber" in Ollama than in llama.cpp, it may not be your imagination. It may be the extra layer of abstraction introducing parsing or formatting errors. One HN commenter described debugging a reasoning loop bug in Step 3.7 Flash on llama.cpp that was caused by an extra newline being captured as part of a reasoning block — a parser issue, not a model issue.

**Second, be extremely conservative with KV-cache quantization.** The temptation to squeeze longer context into limited VRAM is real. But INT4 KV cache is not "almost lossless." It is actively destructive for agentic tasks. If you need 100k context and only have 24 GB of VRAM, you may be better off using a smaller model at full precision than a larger model with a crushed KV cache.

**Third, do not trust model-card KL divergence numbers at face value.** The author is explicit: "It is impossible to interpret a number unless the author discloses the reference checkpoints and full runtime environment, evaluation text, calibration data, context lengths, sampled positions, KL direction, any vocabulary truncation, and how the measurements were aggregated. The methodology matters as much as the number, and plenty of people get it wrong."

## The Broader Implication

There is a narrative in AI that local models are catching up to cloud models. Qwen 3.8 27B scores near frontier-level on benchmarks. Gemma 4 runs on a gaming GPU. The gap is closing. This research suggests a more nuanced picture: the *weights* are catching up, but the *infrastructure* around them is not.

A cloud provider like Anthropic or OpenAI controls the entire stack. They choose the attention backend, the quantization strategy, the KV-cache format, and the CUDA kernels. They run A/B tests to see which configuration produces the most helpful tokens. They have teams of engineers whose full-time job is to make sure the math does not drift.

A local user downloads a GGUF from Hugging Face, drops it into an inference engine they barely understand, and assumes the result is the model. It is not. It is the model filtered through a specific software stack, a specific GPU architecture, and a specific set of default settings that may or may not preserve the model's capabilities.

This does not mean local AI is hopeless. It means local AI is harder than the benchmarks suggest. The frontier is not just the weights. It is the weights plus the inference stack plus the operational expertise to keep them aligned. Until the open-source ecosystem closes that gap — with better default configurations, more transparent benchmarking, and tooling that exposes rather than hides these precision effects — the smartest model in the world will still feel dumb if you run it wrong.

The math, as the author reminds us, is math. But the math that gets you from weights to words is a lot more complicated than `pip install ollama` would have you believe.
